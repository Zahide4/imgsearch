Building a Curated 10M

Walking all of Wikimedia Commons returns scanned book pages, herbarium sheets and boundary maps — real photographs of real things, useless for a mood board. This is the replacement: what people actually search for, what Commons actually holds, and how to get ten million images that are worth having.

What Commons actually holds

Category sizes come from the Commons API. The depth probe below is the finding that matters most, and it is easy to get wrong.

Files reachable by recursion depth

Category:Birds2251158,325
Category:Food753,43728,989

Category:Birds holds two files directly and 158,325 by depth three — and that probe capped its own fan-out, so the true figure is higher. Category:Animals holds exactly one file. Read flat, a category crawl returns nothing. Every root in the plan below is walked recursively.

One exception, and it is a gift. Category:Quality images holds 462,631 files in a single flat category, each reviewed by a Commons contributor for photographic quality. It is the highest signal per request available anywhere in this plan, and it is one crawl.

Two buckets are deliberately allocated below their demand. People-and-daily-life and textures-and-backgrounds are the most-searched things on the whole list, and they are exactly what stock photography exists to sell and what Commons does not shoot. Allocating to demand would book volume that is not there to take. This is where the product will be weakest, and no plan fixes it — only a different source would.

The plan

  1. Test the quality gate on images we already have

    Score the 24,000 enumerated images against the keep/drop prompts using the same matmul as the safety filter. This measures the keep rate and calibrates the threshold before anything is built on it. If enumeration filters to something decent, it stays useful as a fallback for categories that run dry.

    30 minutes · no new code

  2. Build recursive category traversal

    Add a discovery mode that walks a category tree instead of the alphabet: generator=categorymembers with a visited set, a depth limit and a frontier that survives in the checkpoint. Everything downstream — fetching, embedding, safety, indexing — is untouched.

    half a day · the only real code

  3. Wire the quality gate into the crawl

    One more prompt group in the scorer already running per batch. Images that fail the gate are never indexed, so the corpus stays clean without a second pass over it later.

    1 hour

  4. Crawl Quality images first

    462,631 vetted files, flat, no recursion needed. It doubles as a live test of the new pipeline against content we know is good — if these come out wrong, the bug is ours.

    about 1 hour of crawling

  5. Pilot one bucket and look at it

    Run nature-and-landscape to roughly 50,000 images, then review a random draw the same way the enumerated corpus was reviewed. Judgement by eye, not by metric. Adjust roots and the gate threshold before committing to the rest.

    1 hour, and the most important hour here

  6. Run the full build

    Forty workers, buckets in allocation order so the corpus is useful at every point rather than only at the end. Roughly eight to ten runs of the workflow.

    1–2 days unattended · $0

What this costs

Nothing but time. The crawl runs on free GitHub runners, the images are served from Wikimedia's own CDN, and the index lives on the €7 box already running. The work is about a day of building, then one to two days of unattended crawling.
