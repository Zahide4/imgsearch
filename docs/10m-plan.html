The one thing that changes

Everything else in the prototype scales. This does not.

Generate and store your own thumbnails. The prototype served images by asking a free shared proxy to resize originals on demand. That single decision produced every serving problem encountered: broken images, 2.5 second museum loads, copy failures, and finally an outright block when we tried to pre-warm the cache.

At 10M the proxy is not a shortcut with rough edges. It is a dependency that rate-limits you, fingerprints your tooling, and cannot be warmed.

The fix is unglamorous and cheap: during ingest, resize once to a 384 px WebP and PUT it to your own bucket. Backblaze B2 charges nothing for uploads and $0.006/GB; Cloudflare R2 charges $4.50 per million writes and $0.015/GB, both with zero egress behind Cloudflare.

At the 22 KB average measured across the prototype corpus, that is $1.32/month at 10M and $13/month at 100M. The thumbnails were never the expensive part — the vector store is.

Pipeline

Five stages, genuinely ordered — each consumes the previous stage's output. Stages 1–4 run offline and can be interrupted; only stage 5 serves traffic.

  1. 01

    Discover by enumeration, not search

    Commons generator=allimages · sharded by gaifrom

    Search only surfaces subjects you thought to type. The prototype's 88 hand-written topics yielded ~143 images each and capped at 12.6k no matter how many machines were added. Enumeration walks the whole namespace instead, and gaifrom splits it cleanly across workers.

    Ask the API for iiurlwidth=800 so it returns pre-rendered thumbnails. Two other approaches were tested and both failed: list=allimages returns only 12,000 px masters, and hand-constructing /thumb/ URLs is the correct MediaWiki form but Varnish answers 400.

  2. 02

    Fetch with per-host limits

    One semaphore per hostname · retry with backoff on 429

    A single global concurrency limit concentrates every request on one origin. Spreading across roughly 14 CDNs and limiting per host takes the failure rate from 60% to 0.6% while raising total throughput, because six in flight to each of fourteen hosts is forty-eight polite requests, not one rude one.

    Honour Retry-After, sleep outside the semaphore, and record why each failure happened. A bare except here hides rate limiting as if it were missing data.

  3. 03

    Resize once, store twice

    pyvips → 384 px WebP → B2/R2 + the embedder

    One derivative serves both purposes: it is the thumbnail users see and the input the embedding model reads. Storing it means changing embedding models later is a GPU pass over your own bucket rather than re-crawling the internet.

    Use pyvips with shrink-on-load, not Pillow. Decoding a 4000 px JPEG at 1/8 scale directly costs ~750 KB of memory instead of ~48 MB, which is the difference between 200 concurrent images and an OOM.

  4. 04

    Embed on rented GPU, in bulk

    SigLIP image tower · streamed from the bucket

    Embedding is never the bottleneck people expect. The image tower benchmarks at 33 img/s on four CPU threads and thousands per second on a rented L4. At 10M this is hours of GPU time costing tens of dollars, not a scaling problem.

    Because stage 3 stored the derivatives, this stage never touches an origin server and can be re-run at will.

  5. 05

    Serve: model in RAM, index beside it

    ONNX Runtime + Qdrant, same region

    The API holds only the text tower; vectors live in Qdrant. Corpus size then costs the API nothing — going from 12k to 500k changed query time by about 3 ms.

    Return JSON only. Thumbnails go browser → CDN directly, never proxied through the API, or every image byte funnels through one box.

Timeline

Wall clock for a 10M build. The phases decouple, so embedding runs on what crawling has already produced rather than waiting for it.

Crawling is the only phase you cannot accelerate. More runners, faster machines and a bigger index box do nothing for it — it is 10M HTTP round trips against a donated service, and the honest limit is what that service should be asked to give. Per-IP rate is what matters: ~12 req/s across 20 addresses is unremarkable; the same volume from one address is not.

At 100M this becomes the wall. Phase 1 scales linearly to roughly two weeks of continuous crawling, which is the point where bulk dumps and mirrors stop being a nicety and become the architecture. Worth investigating before committing, not after.

At 100M, int8 vectors alone are 77 GB and no longer fit. Binary quantization drops them to 9.6 GB, and the HNSW graph — 128 bytes per point at m=16 — becomes the larger consumer at 12.8 GB. Keep full-precision vectors on NVMe and rescore the top candidates.

Storage is never the cost. At both scales the bucket is under a third of the bill; the vector store is the rest.

Measured constraints

Every figure below came from running the prototype against live services, not from documentation. They are the numbers to design against.

82.6/s

Qdrant upsert ceiling, free cluster

Dense + BM25 sparse, 512-point batches, versus 111/s dense-only. BM25 costs ~26% overhead, not the 10× often assumed. This ceiling — not runner count — caps ingest past ~20 parallel workers.

33 img/s

SigLIP image tower, 4 CPU threads

Well above the ~1.75 img/s a crawl worker actually achieves. Embedding is not the bottleneck; fetch concurrency is. Do not buy GPUs to fix a network problem.

1.9 img/s

Embedding on a CI runner, per worker

Measured across a live 20-worker build, and immovable: unchanged by doubling fetch concurrency, and the ceiling on the whole pipeline. Against ~1,000 img/s on a rented L4, this single line is why the phases must be decoupled.

0.29×

ONNX Runtime for the image tower

9.8 img/s against PyTorch's 33.5 on the same four CPU threads. ONNX wins decisively for the text tower — on memory, not speed — and loses badly here. Benchmark per tower; do not generalise.

624 → 293ms

Cold versus warm thumbnail

On-demand resizing means the first viewer of every image waits. Origin dominates the tail: Museums Victoria 2,475 ms and the Met 2,237 ms against Wikimedia's 661 ms. Storing your own thumbnails deletes this row.

60% → 0.6%

Fetch failures, after per-host limits

Same concurrency, spread across ~14 origin CDNs instead of concentrated on one. The original 60% loss was rate limiting misread as missing images.

0.4 req/s

Openverse sustained throughput

Identical authenticated or anonymous; a free API token buys nothing. Anonymous requests are also capped at page_size=20. Excellent for discovery breadth, unusable as a bulk source.

69 img/s

Commons enumeration, 8 shards

500k discoverable in about two hours. extmetadata costs 9× but carries the licence, so it is not optional.

325 MB

Serving footprint, ONNX versus PyTorch

Down from ~2 GB, with identical embeddings. Dropping transformers for tokenizers saves a further 218 MB. This is what fits the API inside a 512 MB free tier.

300 → 7ms

Region pinning the API to the index

Same code, same cluster. Cross-region adds a full round trip to every query. Place the API in the vector store's region before optimising anything else.

Traps that fail silently

Each of these passed tests, produced no error, and degraded quality invisibly. They are worth encoding as assertions in the new build.

4-bit quantization destroys SigLIP text embeddings

q4f16 was 25× faster and looked correct on the first two queries. Measured, unrelated queries scored 0.86–0.97 cosine against each other where the float32 baseline is 0.68–0.76 — the embeddings had collapsed, so one image ranked first for everything. int8 is safe at 0.725.

Gate on it at load: embed two unrelated strings and reject the backend if they are too similar. Note the threshold must be measured, not guessed — SigLIP embeddings are uncentered, so a naive < 0.6 check rejects every working backend.

Token padding must stay at 64

Most queries are three tokens, so padding to 16 looks like a free 3× speedup. Cosine against the pad-64 reference collapses to 0.45–0.63: SigLIP's position embeddings depend on the trained padding length.

Hand-rolled tokenizers need two fixes or search quietly degrades

Swapping transformers for tokenizers saves 218 MB but changes behaviour twice: pad with token id 1, not 0, and apply SigLIP's canonicalization — lowercase, strip punctuation, collapse whitespace — before encoding. Without it, "A Steam Locomotive!" tokenizes to something entirely different from "a steam locomotive".

MediaWiki continuation cursors are not always URL-safe

Commons holds filenames in decomposed Unicode. Echo one back as a gaicontinue value and the API answers urlparamnormal and the worker dies mid-range — two of twenty did, about 23 pages in. NFC-normalize every outgoing parameter, and treat the error as recoverable: one unrepresentable cursor should cost a range, not a worker.

An optimisation that works on one tower can reverse on the other

ONNX Runtime cut the text tower's footprint from ~2 GB to 325 MB with identical embeddings, so applying it to the image tower looked obvious. It runs at 0.29× PyTorch's speed, and the quantized variant that is fast drifts to 0.977 cosine. Measure each one.

"Commercial use" filters still return no-derivatives licences

Openverse's license_type=commercial includes ND, which permits commercial use but forbids the cropping and compositing an editor does constantly. Whitelist cc0,pdm,by,by-sa explicitly, and surface share-alike separately — it is viral onto derivatives and nobody reads the terms.

Photographer names do not belong in a lexical index

Including creator in the BM25 text makes a query for "williams" match every photo by Phil Williams, and floods the sparse index with high-cardinality tokens that dilute IDF against real subject terms.

Markup leaks in through source metadata

Openverse returns microformat HTML in some titles. At 0.5% of a 12,345-image corpus it is cosmetic; at 10M it is 50,000 records feeding div, class and style into the search index. Strip tags at ingest, not at render.

Retrieval

Dense vectors alone cannot distinguish proper nouns. Searching Herstmonceux Castle against a SigLIP-only index returns Leeds Castle and Broncroft Castle first, because the model understands "castle" perfectly and the name not at all.

Fusing a BM25 sparse vector over title, description and tags with reciprocal-rank fusion puts the correct castle first, at a cost of roughly 60 ms. Keep both prefetches filtered identically and preserve quantization rescoring on the dense branch.

One caveat worth planning around: BM25's value depends on metadata quality, and enumeration produces thin metadata. Search-sourced records carry real tags; enumerated ones often carry a filename like Ph-1.jpg. Expect hybrid to help less as enumeration comes to dominate the corpus, and consider a VLM captioning pass over whatever your query logs show people actually look at.

Open risks

Unresolved at the end of the prototype. Each needs a decision before or during the real build.

  • Legal
    Trademark and publicity rights are separate from copyright

    A commercially-licensed photograph of a branded object is still not commercially usable. CC-licensed photographs of people almost never carry model releases. The licence filter answers a narrower question than users assume it does.

  • Coverage
    The categories professionals want most are the ones free sources have least

    Measured on the prototype: transparent cutouts and clean product shots scored near noise, roughly 0.04 against 0.15 for well-covered subjects. If those queries matter, background removal becomes a core feature rather than a nicety.

  • Quality
    Enumeration trades relevance for volume

    Walking the namespace returns everything, including 365 consecutive scans of one manuscript. Deduplication and a quality filter matter far more at 10M than at 12k.

  • Provenance
    Licence metadata must be stored as fetched, with a timestamp

    Upstream sources contain mislabelled files, and serving an all-rights-reserved image as CC0 is direct liability rather than the uploader's. Recording the source URL, the exact licence string and the fetch time is a schema decision — cheap now, a migration over 10M rows later.

  • Ingest
    Crawling 10M originals is weeks, not hours

    Bandwidth is free; politeness is not. Distributed IPs move the throttling offline where users never see it, but the wall clock is real and should be budgeted alongside compute.
