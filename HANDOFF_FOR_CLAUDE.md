## Starting and completing the bulk build

After migration, validation, commit, push, and successful Render deployment,
the count should still be 12,345. To land at 500,001, use 121,914 new records per
worker across four workers:

```sh
gh workflow run cloud-corpus.yml \
  -f target_per_worker=121914 \
  -f build=commons-500k-v1
```

The workflow and script deliberately stop before GitHub's maximum job duration.
When a run checkpoints and exits incomplete, rerun the exact same build ID and
target; each worker resumes its Hugging Face cursor and its Qdrant count. Expect
roughly five workflow runs based on the pilot. Never change the worker count for
an active build ID.

Monitor on every run:

- all four worker logs and image-fetch failure counts;
- `images-v2` point count and green status;
- Qdrant disk/RAM/headroom and indexing progress;
- representative semantic and exact-name query quality/latency;
- sample thumbnail status, payload size, and load time;
- Hugging Face archive/checkpoint uploads.

The Qdrant free cluster advertises 1GB RAM and 4GB disk. The dense originals alone
are about 1.54GB at 500k; int8 vectors are about 384MB, with additional HNSW,
sparse-index, payload, and operational headroom. The design is plausible within
4GB but 500k is not proven until metrics are observed during growth. Stop before
exhausting disk or RAM rather than corrupting availability. Hugging Face public
storage beyond the free best-effort allowance is also not a guarantee.

At exactly/just above 500k, stop rerunning the workflow and verify the public
Render site, `/api/stats`, several cold/cached searches, license filters, image
loading, source/full URLs, Qdrant health, and final archive/checkpoint state.
